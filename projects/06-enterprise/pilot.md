## 1. Engagement boundary and sponsor decisions

Question: can earlier data triage reduce repeated packet handling **without
worsening clean-quote tails or shifting unacceptable waiting to another role?**
The pooled pod is retained as a counterexample, not selected on its fast clean path.

In scope: independent exact-money checks; synthetic quote-readiness routing;
local no-send queue replays; proposed owner handoffs; bounded practice and metrics.
Out of scope: invoices, payment, tax determination, credit authorization or
reservation, production data, enterprise credentials, ERP writes, live integrations,
notifications, purchases, access changes, hiring, and native Hive activation.

Before any rehearsal, an owner would need to:

1. Confirm that only these labeled synthetic inputs are used and designate
   temporary practice roles without granting production privileges.
2. Review assumptions, especially 6/18/10/12 baseline minutes, triage's 12-minute
   intake, faster validation, the pod's 1.5× preparation penalty, and unequal slot
   counts. These are value hypotheses, not source observations.
3. Agree to the paired-input protocol, all-case denominators, adverse-metric stop
   conditions, and retention of originals and unsuccessful runs.
4. Recognize that source correctness and modeled speed do not establish actual
   policy, user comprehension, readiness authority, savings, or adoption.

Real commercial/tax/account policies, any real data collection, and any enterprise
access would each need a **separate** approved scope. This pack is not that approval.
The seed's fictional two-workday lag is not a measured baseline.

## 2. Bounded no-production pilot design

Proposed limit: **10 working days or five paired eight-quote batches (40 synthetic
submissions), whichever comes first**. Each submission is replayed through baseline
and triage; do not count the paired replay twice. Pooled-pod comparisons remain
visible as a sensitivity check, not a production candidate.

- Preserve the exact eight source cases and original exception reasons.
- Declare the arrival/owner/final-desk condition **before** each pair. Use identical
  input versions, arrival clocks, and common stress multipliers within the pair.
- Include the primary condition, simultaneous arrivals, slow owners, and slow
  final desk. Do not discard adverse runs or select only completed clean cases.
- Collect only a local, synthetic practice ledger. Never upload enterprise exports.
- End at recorded pending handoff: two clean-but-unapproved, four review-pending,
  two data-held. No participant is asked to make a real approval or correct originals.

The deterministic simulations in `results/` have run. The proposed human rehearsal
has **not** run. Repeating the same deterministic fixture is not new empirical
evidence or an increased independent sample size.

## 3. Measurement contract

Capture batch/condition, input SHA-256, immutable source quote ID, assumed arrival,
source completeness, queue entry, service start/end, resource/slot, source reason,
proposed role, each return, and final pending state. Preserve every incomplete
case and attempted return. No original value is overwritten.

| Measure | Denominator/window | Interpretation |
|---|---|---|
| Model queue wait | Sum of queue intervals per case, all 8 submissions | Excludes service and unknown external response time |
| Model cycle | Original assumed arrival to recorded pending handoff | Includes incomplete submissions; not a live approval clock |
| Handoff throughput | All 8 pending handoffs / first-arrival-to-last-handoff hours | Includes unresolved holds; never cash or accepted-quote throughput |
| Tail burden | Nearest-rank p95 for all 8; clean tail separately for the 2 originally clean cases | n=8 p95 is max; no statistical confidence interval |
| Packet rework rate | Cases with ≥1 modeled recheck / all 8 | 6/8 in all designs; not measured real source-data rework |
| Return visits | All unchanged-input recheck visits | 8 baseline/pod, 6 triage; all underlying reasons persist |
| Resource burden | Busy slot-minutes/(slots × horizon), queue area, peak queue | Report each role; do not hide relocated bottlenecks |
| Incorrect clean classification | Wrongly clean original quotes / all quotes | Must remain zero in the modeled fixture |
| Comprehension | Correct explained distinctions / proposed prompts | Not observed until a separately approved rehearsal occurs |

If a later real baseline is independently approved, collect **complete-submission
to actual human disposition** separately from first incomplete submission,
stratify incomplete and review cases, and include all submissions in the rework
denominator. That would implement the seed's proposed real lead-time definition.
The current model's arrival-to-packet cycle is **not** a substitute. Real sampling,
variability, consent, labor cost, financial impact, and savings remain unknown.

No training session or attendance is asserted.

|---|---|---|

| 5–13 | Seller traces q-101 vs. q-105 | Both missing PO and unknown tax identified; no invented replacement |
| 13–21 | Credit reviewer traces q-102 | 1036.10 exposure explained without reserving or authorizing credit |
| 21–28 | Billing coordinator checks q-106 and q-104 | 0.01 tiny-line tax and 849.92 rounded q-104 net explained |

## 6. Guardrails, rollback triggers, and exit

**Immediate stop** on any of:

- missing/duplicated case; mismatch between submitted and accounted-for work;
- capacity overflow, inconsistent clock arithmetic, or non-reproducible output;
- altered source bytes, unmatched comparison inputs, or an unmodeled reason;
- a data-null interpreted as zero, a “clean” result treated as approval, or an
  unsupported policy default;
- any real data, attempted external effect, production connection, invoice,
  payment, credential use, or automated outreach.

**Metric stop:** after **two paired batches**, stop the redesign if all-case p95
queue wait is >10% worse **or** clean-case tail is >15% worse than the matched
baseline. These are proposed owner guardrails, not validated service levels.
Also require an owner review of any materially increased role queue, even if the
two aggregate thresholds pass. Do not move a waiting problem onto an unseen team.

The slow-final-desk simulation already gives a warning: triage's clean tail is
180 vs. 150 minutes (+20%), despite faster drainage. Repeating that condition in
two paired rehearsals would trigger the proposed rollback. Under slow owners,
the pod's p95 wait is 194 vs. 132 and drain time is 390 vs. 280; it must not be
chosen just for its 78-minute clean path.

**Rollback procedure:** pause the local replay; retain the input hash, both
trajectories, and the triggering observation; select Baseline and Reset; stop the
offline exercise. Keep original data and clearly label any rehearsal notes. No
production state was created, so there is no production migration, backup restore,
or live change to undo. This is a genuine stop/revert boundary, not a claim that
an unperformed deployment was rolled back.
