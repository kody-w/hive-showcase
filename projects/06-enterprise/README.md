# Process Time Machine

**Workstream 06 · enterprise-transformation-firm · work-produced**

An original, dependency-free, local-only quote-to-cash **readiness** simulator.
Replay the same eight Lattice Harbor Supply quotes through a baseline, an
early-triage redesign, and a pooled exception pod. Follow every queue, service
slot, exception packet, and unchanged-input return.

**All business inputs are SYNTHETIC. All clocks, service times, capacities, and
redesign effects are assumptions. Modeled improvement is not realized savings.**
Nothing issues invoices, authorizes credit, supplies source corrections, collects
cash, contacts people, or changes production. No native Hive setup occurred.

## Open and reproduce

The entrypoint is `projects/06-enterprise/index.html`, relative to the repository
root. Open it through the parent's owner-controlled local static preview. Plain
browser ES modules and a same-origin fixture read are required; `file://` can
block them. This project starts no server and makes no external requests.
There is no dependency install, CDN, analytics, storage, or service worker.

From the **repository root**, using Node 20+:

```sh
# Read-only validation: unit/UI-adapter tests, exact source hashes,
# reproducible artifact bytes, manifest/local links, and recorded integrity.
node projects/06-enterprise/scripts/validate.mjs

# Explicitly regenerate only this project's three deterministic artifacts:
node projects/06-enterprise/scripts/reproduce.mjs --write

# Re-run actual checks and persist a new validation receipt:
node projects/06-enterprise/scripts/validate.mjs --record
```

```sh
node projects/06-enterprise/scripts/reproduce.mjs --check
```

The result receipt records actual exit codes, test counts, runtime version, source
verification, input SHA-256 values, measured-in-model comparisons, and scoped

No downloaded reference Python or tests are executed, imported, or embedded.

Quotes are evaluated independently without changing open balances or reserving credit.

## Three explicit hypotheses

All quantities below are model assumptions, not staffing observations or SLAs.
Continuous integer working minutes; no shifts, outages, preemption, or randomness.

| Design | Intake | Initial validation | Each return | Final handoff | Specialist preparation |
|---|---:|---:|---:|---:|---|
| Baseline | 6 | 18 | 10 | 12 | One slot per proposed specialist role |
| Triage first | 12 | 6 | 6 | 12 | Same capacities; consolidate reasons before one return |
| Pooled pod | 6 | 10 | 10 | 12 | Two generalist slots; each exception takes 1.5× |

Baseline/triage each have eight slots: intake, billing, seller-data, tax-data,
credit, commercial, account, disposition, one each. The pod replaces five
specialist slots with two shared generalists: **five total**, not an equal-staffing
comparison. These slots are not a measured labor budget or a cost-saving claim.

Specialist packet-preparation times: missing PO 24, tax confirmation request 30,
quantity correction request 24, inactive-account review packet 30, credit packet
36, discount packet 24, terms packet 24 minutes. Source-reason order is fixed:
PO, tax, quantity, account, credit, discount, terms (ties by exact reason string).

- **Baseline:** intake → billing → each exception owner → billing recheck after
  each reason → final disposition packet.
- **Triage:** longer upfront intake → clean/calculable cases use faster billing;
  known data-blocked cases bypass that initial billing visit → collect every
  exception packet → one consolidated billing return → final disposition.
- **Pod:** baseline-style return structure, faster assumed billing packet
  assembly, but pooled preparation capacity and slower generalist exception work.
  Accountable business roles do not transfer approval authority to the pod.

**Rework semantics:** a return is a re-evaluation of the **same unchanged source**.
Baseline/pod perform eight return visits across six cases; triage performs six.
No probability of successful correction is invented. Service at an owner desk
means preparing a request or review packet, not receiving a decision. The finite
simulation ends when that pending handoff is recorded. External approval and
data-resolution time are unresolved and unbounded by this model.

`pf-lag`'s fictional two-workday handoff statement is not used as an empirical
calibration. All assumptions, including the stress multipliers, are exposed in
`model.mjs`, the UI, and the generated comparison artifact.

## Discrete-event contract and metrics

`engine.mjs` is a pure original simulator. It validates every case/resource/route,
clones inputs, processes finite positive-duration tasks, and drains all cases.
At a tied clock: finish tasks in scheduling order, enqueue their returns, enqueue
new arrivals in quote-ID order, then dispatch FIFO by enqueue sequence. Resource
dispatch order is resource ID; the lowest free slot is used. Intervals are
**[start, end)**. Snapshots are after all events at the chosen time.

Every visit persists resource, slot, reason, owner where applicable, queue time,
service start/end, wait explanation, and rework identity. Each case obeys:

`cycle = total FIFO wait + total service`

Conservation is checked at every event and between events:

`8 = not arrived + queued + in service + recorded handoff`

- **Drain duration:** last handoff minus first arrival; not a real quote-to-cash cycle.
- **Throughput:** all 8 pending handoffs / drain duration × 60. Includes the 2 data
  holds and 4 pending reviews. Not invoices, approved quotes/hour, or steady-state capacity.
- **Case cycle:** original modeled submission to handoff; includes incomplete
  submissions. This differs from the seed's proposed real complete-submission metric.
- **Wait distribution:** per-case summed queue time; min/mean/p50/p95/max across all
  eight. Nearest-rank percentiles; with n=8 p95 equals max. Clean tail uses n=2.
- **Packet rework rate:** cases with ≥1 recheck / all submissions = 6/8 in all
  designs. Fewer return visits is not evidence that real source-data rework fell.
- **Resource utilization:** busy slot-minutes / (capacity × run duration).
  Elapsed utilization uses the clipped replay horizon and freezes after drainage.
- **Bottleneck:** greatest summed case waiting at a resource, with ID tie-break;
  not necessarily highest busy percentage. Peak queues exclude zero-duration waits.

### Reproduced primary comparison

**Authored ladder only; these are measured in the model, not observed operations.**

| Design | Drain min | Handoffs/h | Mean wait min | p95 wait min | Clean tail min | Largest wait |
|---|---:|---:|---:|---:|---:|---|
| Baseline | 248 | 1.935 | 71.75 | 98 | 76 | Billing validation |
| Triage first | 162 | 2.963 | 16.75 | 32 | 58 | Seller intake |
| Pooled pod | 223 | 2.152 | 26.00 | 54 | 28 | Shared exception pod |

Triage reduces the model's primary drain duration by 86 minutes, **but final-desk
queue time grows from 14 to 48 summed case-minutes**. The bottleneck did not vanish.
All three still end at exactly **2 clean/unapproved, 4 review-pending, 2 data-held,
0 approved**.

### Predeclared stress conditions expose regressions

- **Synchronized burst:** same 8 quotes, all at t=0. Baseline/triage/pod mean
  waiting becomes 106.75 / 51.75 / 62.50 minutes; p95 waiting 154 / 102 / 112.
- **Slow exception owners:** same burst, all designs double owner-preparation
  service. The pod drains in **390 vs. baseline 280 minutes**; throughput falls
  to **1.231 vs. 1.714** and p95 waiting rises to **194 vs. 132**. Clean-case tail
  improves (78 vs. 126), demonstrating why that one metric cannot choose a design.
- **Disposition desk squeeze:** same burst, final service is 36 rather than 12
  minutes for everyone. Triage drains faster (**324 vs. 376**) but its clean-case
  tail worsens **180 vs. 150 minutes** and final-desk waiting grows **528 vs. 310**.
  Its largest waiting location moves to the disposition desk.

The UI reports every scenario/design combination, all individual waits, and
regressions. [results/comparison.json](results/comparison.json) retains full
metrics, per-case totals, capacities, and identical-input SHA-256 values for all
12 runs. [results/replays.json](results/replays.json) retains complete event logs
and per-visit histories for the three primary runs. Stress histories are regenerated
by the same exported `runAllComparisons` function used in the UI/tests.

## Validation and limitations

Tests cover exact seed hashes and eight monetary outcomes; malformed/duplicate/
orphan inputs; data precedence and policy boundaries; hand-calculated one- and
two-slot queues; completion/arrival ties; deterministic replay; no mutation;
case conservation and capacity at every transition; metric arithmetic and queue
area; every exception and bounded rework return; identical comparison inputs;
both unfavorable stress results; persisted artifact byte identity; UI reducers,
renderers, control/event wiring, load failure, and timer stopping with an injected
DOM/clock adapter.

**No browser was used.** Node DOM-adapter tests are not a visual, accessibility,
or cross-browser audit. The parent may separately preview the UI. No human
review, rehearsal, owner approval, deployment, financial impact, or market
validation is claimed.

Eight deliberately authored quotes are not representative production data.
Durations, capacity, deterministic FIFO, continuous time, no failures, the
generalist multiplier, and faster validation are uncalibrated hypotheses. There
are no confidence intervals or long-run throughput claims. Real source correction,
approval, concurrency-safe account credit, inventory, tax jurisdiction, invoices,
fulfillment, returns, payment, integration, and cash timing are outside the boundary.
Even the better modeled design must pass separate policy, access, human, and
tail-risk gates before any independently authorized real pilot.
